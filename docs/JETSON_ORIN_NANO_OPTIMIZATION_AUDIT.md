# SiamRAM — Jetson Orin Nano Optimization Audit

Date: 2026-06-17
Author: Claude (independent code scan)
Scope: **Exploration only. No runtime behavior is changed by this document.**

This is a from-scratch read of the actual code (hot path, TRT engines, I/O, config,
deps, container) to find *behavior-preserving* speed/memory wins for deploying the
tracker on a **Jetson Orin Nano**.

## TL;DR — the delta vs the GPT report

**Genuinely new, behavior-preserving wins the GPT report missed:**

1. **`[NEW]` Frame decode is fully serialized with GPU work.** `cv2.imread()` runs
   inline before each `tracker.update()` ([vis/test_model.py:376](../vis/test_model.py#L376)).
   A one-thread prefetch (read frame N+1 while the GPU tracks frame N) hides JPEG
   decode behind compute. On the Orin's weak CPU this is likely the single biggest
   easy throughput win for image-sequence inputs. Same frames, same order → identical output.
2. **`[NEW]` Dead `albumentations` dependency on the hot path.** The normalize
   transforms are built at init but **never applied** — `_preprocess_image` ignores
   its `transform` argument and re-does normalization on GPU
   ([base_tracker.py:214-222](../models/SiamABC/tracker/base_tracker.py#L214-L222)).
   `albumentations` is a heavy import; dropping it from the runtime path cuts startup
   time and one fragile Jetson dependency.
3. **`[NEW]` `box_coder.decode()` does two separate `.item()` GPU syncs every frame**
   ([box_coder.py:397-398](../utils/box_coder.py#L397-L398)). Collapsible to one.
4. **`[NEW]` No global `cudnn.benchmark`.** Input shapes are fixed (YOLO 320², attention
   at two fixed sizes); enabling autotune is a one-liner and behavior-preserving.
5. **`[NEW]` YOLO TRT export is hard-coded FP32** (`half=False`,
   [tracker.py:3556](../models/siamram/tracker.py#L3556)) — relevant only if you ever
   enable YOLO TRT, but it means "compiled YOLO" is currently leaving ~2× on the table.
6. **`[NEW]` Hardware reality check:** the Orin Nano has **no DLA** and **unified
   memory** — both change which optimizations are worth doing (details below).

**The GPT report's two real P0s are correct and verified:** per-clip YOLO reload, and
the per-frame `float(lam.item())` sync. Keep those.

## The per-frame hot path (where the time actually goes)

Normal tracking, per frame, in order
([_update_impl](../models/siamram/tracker.py#L954) → [_normal_update](../models/siamram/tracker.py#L1415)):

| Step | Work | Device | Notes |
|---|---|---|---|
| 1 | `_prescale_frame` | CPU (cv2.resize) | no-op if already ≤ cap |
| 2 | `_estimate_homography` | **CPU** (optical flow) | `calcOpticalFlowPyrLK` on a downscaled gray frame, **every frame** |
| 3 | `_is_heavy_camera_motion` | CPU | cached per `frame_idx` (called twice, computed once — verified OK) |
| 4 | EKF predict | CPU (numpy) | cheap |
| 5 | `tracker.update` → SiamABC forward + decode | **GPU** | TRT backbone/attention/connect; **~5–6 GPU→CPU syncs** in decode/postprocess |
| 6 | descriptor (OSNet) | GPU | strided (`descriptor_stride=2`), overlapped on side stream when enabled |
| 7 | EKF update + history bookkeeping | CPU (numpy) | cheap |

Two structural facts about Orin matter here:

- **Steps 1–2 are CPU and serialized with the GPU steps.** Optical flow + JPEG decode
  are the CPU tent-poles; the Orin Nano CPU (6× A78AE, frequently thermally limited)
  is the scarce resource, not the GPU.
- **Every GPU→CPU sync in step 5 stalls the pipeline.** On the Orin's *unified* memory
  the *copy* is cheap, but `.item()`/`.cpu()` still force a stream synchronize, which
  serializes CPU and GPU. Removing syncs helps for the stall reason, not the bandwidth reason.

## New findings (detail) — not in the GPT report

### `[NEW]` P0 — Decode/compute are serialized; add a prefetch thread

In the production fast path ([vis/test_model.py:370-380](../vis/test_model.py#L370-L380)):

```python
def _read_next_frame():
    ...
    frame = cv2.imread(frame_paths[frame_ptr])   # blocking JPEG decode
    ...
# loop:
ret, frame = _read_next_frame()   # CPU decode
result = _update(frame)           # GPU pipeline — waits for decode to finish first
```

The JPEG decode of each frame happens **inline**, then the GPU pipeline runs, then the
next decode happens. Decode and compute never overlap. On a discrete-GPU workstation
this is masked by a fast CPU; on the Orin Nano the CPU is the bottleneck and a 1080p+
JPEG decode (~5–15 ms) is paid in full every frame.

Fix (behavior-preserving): a single-slot producer thread (or a tiny 2–3 deep queue)
that decodes frame N+1 while `update()` processes frame N. Frame identity and order
are unchanged, so output is bit-identical. Applies to both the directory-of-images
path (`cv2.imread`) and the video path (`cap.read()`).

Validation: regression test parity; compare per-frame bbox files byte-for-byte;
measure wall-clock FPS before/after.

### `[NEW]` P1 — `albumentations` is imported and built but never used at runtime

`base_tracker.py` imports `albumentations` and constructs three normalize transforms
plus `_get_default_transform` ([base_tracker.py:14,107-115,176-191](../models/SiamABC/tracker/base_tracker.py#L176-L191)).
But the actual preprocessing ignores them:

```python
def _preprocess_image(self, image, transform=None):   # transform arg unused
    x = torch.from_numpy(image[:, :, :3]).permute(2,0,1).unsqueeze(0).float()
    x = x.to(self.cuda_id, non_blocking=True).div_(255.0)
    return x.sub_(self._norm_mean).div_(self._norm_std)  # GPU normalize, not albu
```

Callers pass `self._template_transform` / `self._search_transform`
([SiamABC_Tracker.py:346,408](../models/SiamABC/tracker/SiamABC_Tracker.py#L346)) but
the base method drops them. So the albumentations import, the `Compose`, and all three
transform objects are dead weight. (`_array_to_batch` at
[base_tracker.py:132](../models/SiamABC/tracker/base_tracker.py#L132) is likewise
unreferenced.)

Why it matters on Orin: `albumentations` pulls a non-trivial import tree
(`scipy`/`scikit-image`-adjacent) and adds cold-start time and one more package that
must resolve to ARM/JetPack-compatible wheels. Removing it from the runtime path is
pure cleanup with zero behavioral effect because it is already not executed.

Validation: delete the import + transform construction, run the regression harness —
outputs must be identical (they already are).

### `[NEW]` P1 — Add a global `cudnn.benchmark = True` (and friends) at startup

Nowhere in the codebase is `torch.backends.cudnn.benchmark` set (verified by grep).
The non-TRT GPU work runs at **fixed** shapes:

- eager YOLO (`copile_yolo: false` in the shipped config → ultralytics runs the `.pt`
  model) at a fixed `imgsz=320`,
- the `torch.compile` FP32 attention neck, exercised at exactly two spatial sizes
  ([siamabc.py:246-256](../models/SiamABC/tracker/trt_engine/siamabc.py#L246-L256)).

`cudnn.benchmark = True` lets cuDNN autotune the fastest convolution algorithm for each
fixed shape after a couple of warmup iterations. It is behavior-preserving (same math,
different kernel selection). One line at process start.

> Note: `torch.backends.cuda.matmul.allow_tf32` / `cudnn.allow_tf32` would also help the
> FP32 attention/connect stages, but those **change numerics** (TF32 truncates the
> mantissa). The connect head is deliberately FP32 for score precision — see
> [siamabc.py:30-36](../models/SiamABC/tracker/trt_engine/siamabc.py#L30-L36) — so TF32
> belongs in the "benchmark first" bucket, not here.

### `[NEW]` P2 — `box_coder.decode()` does two `.item()` syncs per frame

[box_coder.py:395-398](../utils/box_coder.py#L395-L398):

```python
flat_idx = torch.argmax(cls_map)
H, W = cls_map.shape
r_max = (flat_idx // W).item()   # sync 1
c_max = (flat_idx % W).item()    # sync 2
```

Two device→host scalar reads where one suffices:

```python
flat = int(flat_idx.item())      # single sync
r_max, c_max = divmod(flat, W)
```

Small but it runs every frame and every Phase-3 verification. Best folded into the
broader postprocess-coalescing work (next item).

### `[NEW]` P3 — CPU thread oversubscription

OpenCV's `calcOpticalFlowPyrLK`, `goodFeaturesToTrack`, and the JPEG decoders all spawn
worker threads. With the main Python loop, the SiamABC stream callbacks, and ultralytics
all live, these can oversubscribe the Orin's 6 cores and *increase* latency variance.
There is no central thread control today.

Lever: `cv2.setNumThreads(n)` and `torch.set_num_threads(n)` tuned for the Orin (often
`n=4` beats `n=6` once thermal throttling kicks in), plus the usual `OMP_NUM_THREADS`/
`OPENBLAS_NUM_THREADS`. This is the specific, measured version of the GPT report's
generic "thread knobs" suggestion. Behavior-preserving (scheduling only).

### `[NEW]` Hardware-specific guidance

- **No DLA on Orin Nano.** Unlike Orin NX/AGX, the Nano modules ship with the DLA
  fused off. Do **not** spend time trying to place TRT engines on DLA — it will fall
  back to GPU or fail. (Worth stating because it's a common Jetson "optimization"
  rabbit hole.)
- **Unified memory.** CPU and GPU share LPDDR5. Host↔device *copies* are cheap, so the
  payoff from removing `.cpu()`/`.item()` calls is eliminating **pipeline stalls /
  stream syncs**, not saving PCIe bandwidth. It also means `non_blocking=True` on the
  pageable tensor at [base_tracker.py:221](../models/SiamABC/tracker/base_tracker.py#L221)
  is effectively a no-op today (no pinned buffer), but chasing pinned memory is low
  value on unified memory — skip it.
- **4 GB vs 8 GB matters.** The resident set is torch + torch-tensorrt runtime +
  SiamABC-M FP16 engine + OSNet-x0.25 FP16 engine + YOLO11n + Python. On a **4 GB**
  Nano this is tight; the pandas submission materialization (below) and any full-split
  in-memory buffering are the parts most likely to push it into swap.

## Confirmed / extended from the GPT report

### P0 (confirmed) — Per-clip YOLO reload

Verified: each sequence builds a **fresh** wrapper unless `--reuse_tracker`
([run_inference.py:1570-1572](../run_inference.py#L1570-L1572)), and the wrapper
constructor builds YOLO every time ([tracker.py:390-392](../models/siamram/tracker.py#L390-L392),
via [load_yolo_compiled](../models/siamram/tracker.py#L3529)). For a full split that is
one YOLO load per clip.

Sharpening: OSNet does **not** have this problem — it's a process-global singleton
(`_OSNET_EXTRACTOR`, [utils.py:675-697](../utils/utils.py#L675-L697)), so it is built
once regardless of wrapper churn. **Only YOLO** reloads. The clean fix is exactly the
GPT one: a YOLO object cache keyed by (weights, imgsz, device, engine-mode), injected
into each fresh wrapper while sequence-local state stays fresh.

### P0 (confirmed) — Per-frame `float(lam.item())`

Verified at [siamabc.py:489](../models/SiamABC/tracker/trt_engine/siamabc.py#L489),
inside `track()` which runs every frame. The fix is clean because the TTA mode is
*already* Python-known: `set_tta()` writes `self._tta_lam.fill_(val)`
([SiamABC_Tracker.py:1100-1101](../models/SiamABC/tracker/SiamABC_Tracker.py#L1100-L1101)).
Cache a Python bool/float there and pass it into `_dispatch_connect` instead of reading
the CUDA scalar back each frame.

### P1 (extended) — Coalesce the SiamABC decode/postprocess syncs

The GPT report says "copies small maps/scalars to CPU each frame." Concretely, the core
SiamABC forward+decode does roughly **5–6 device→host syncs per frame** (IoU head is off
in config, so its two are not counted):

| Sync | Location |
|---|---|
| `float(lam.item())` | [siamabc.py:489](../models/SiamABC/tracker/trt_engine/siamabc.py#L489) |
| `(flat_idx // W).item()` | [box_coder.py:397](../utils/box_coder.py#L397) |
| `(flat_idx % W).item()` | [box_coder.py:398](../utils/box_coder.py#L398) |
| `cls_score.squeeze().cpu().numpy()` | [SiamABC_Tracker.py:954](../models/SiamABC/tracker/SiamABC_Tracker.py#L954) |
| `penalty.cpu().numpy()` | [base_tracker.py:336](../models/SiamABC/tracker/base_tracker.py#L336) |
| `decoded_info.bbox.cpu().numpy()` | [base_tracker.py:276](../models/SiamABC/tracker/base_tracker.py#L276) |

The peak cell, its 4 bbox edges, and the peak score can all be selected on-GPU, then
copied to the host in **one** tiny transfer. That collapses ~6 stalls into ~1. This is
the highest-value hot-path cleanup, but it touches numerically sensitive code
(penalty/window/smooth), so it needs careful golden-output validation. Medium effort.

### P2 (confirmed) — Jetson-incompatible dependencies

`pyproject.toml` pins `torch==2.11.0`, `torchvision==0.26.0`, `torch-tensorrt==2.11.0`,
`triton==3.6.0`, all from the `pytorch-cu128` index. None of those install on JetPack/L4T
— Jetson needs NVIDIA's aarch64 torch wheels and the TensorRT that ships with JetPack
(plus a matching `torch-tensorrt` build). On top of that the **runtime** env carries
dev/training libs: `wandb`, `tensorboard`/`tensorboardx`, `matplotlib`, `ipython`/
`ipykernel`/`ipywidgets`, `scikit-learn`, `spikingjelly`, `got10k`, `lmdb`,
`pycocotools`, `gdown`. Recommend a `pyproject.jetson.toml` (or extras split) with only
the inference runtime, and a JetPack base image (see container note).

### P2 (sharpened) — `.dockerignore` / container

`containers/Dockerfile.gpu` is `FROM nvidia/cuda:12.8.1-base-ubuntu22.04` — an x86 CUDA
base that won't run on Jetson; use an `nvcr.io/nvidia/l4t-*` / JetPack base instead.

The `.dockerignore` excludes only **top-level** checkpoint globs
(`checkpoints/*.pt|*.pth|*.onnx|*.engine`). It misses:

- **`*.ts`** entirely — and `.ts` is *the* TRT cache extension this repo writes
  ([siamabc.py:373](../models/SiamABC/tracker/trt_engine/siamabc.py#L373),
  [osnet.py:82](../models/SiamABC/tracker/trt_engine/osnet.py#L82)). These get copied
  into the build context.
- **Nested** caches (`checkpoints/trt_engines/**`, `checkpoints/reid/**`).

Use recursive ignores (`checkpoints/**/*.ts`, `checkpoints/**/*.engine`, …) and mount
caches at runtime. (TRT engines are GPU/driver/version-specific anyway — a cache built
on the workstation is invalid on the Orin and must be rebuilt on-device.)

### P3 (confirmed + `[NEW]`) — YOLO compile path

- `copile_yolo` is a typo'd kwarg/config key ([tracker.py:229](../models/siamram/tracker.py#L229),
  config line 150) — GPT noted this; support `compile_yolo` as an alias.
- `[NEW]`: even when enabled, the export is **FP32** — `model.export(format="engine",
  half=False, device=0, ...)` ([tracker.py:3556](../models/siamram/tracker.py#L3556)).
  On Orin, FP16 YOLO is ~2× faster. But FP16 changes detector numerics, so treat
  enabling it (and `half=True`) as a benchmarked behavior change, not a free win. The
  `.pt`→`.engine` cache name also ignores imgsz/precision/device, so stale engines can
  silently mismatch — fingerprint it like the SiamABC/OSNet caches do.

## Behavior-CHANGING levers (measure before shipping — NOT in the "safe" set)

These can speed things up but alter outputs or accuracy. Benchmark against the
regression harness and the leaderboard metric first.

- **FP16 YOLO TRT** (`half=True` + enable compile): ~2× detector speed, changed numerics.
- **INT8** for OSNet and/or YOLO: big Tensor-core win on Ampere, needs calibration and
  accuracy validation.
- **TF32** on the FP32 attention/connect stages: faster matmuls, reduced mantissa — may
  perturb borderline scores the occlusion thresholds key off of.
- **SiamABC model size M→S**: large speed/memory win, accuracy regression likely.
- **OSNet static-batch-1 engine → fixed batch>1**: today the engine is static batch 1
  and the extractor loops per crop ([osnet.py:10-20](../models/SiamABC/tracker/trt_engine/osnet.py#L10-L20),
  [utils.py:201-210](../utils/utils.py#L201-L210)). A batched engine (batch =
  `osnet_max_candidate_batch`) would cut per-launch overhead during multi-candidate
  occlusion frames. Numerically equivalent, but requires solving the dynamic-reshape
  issue the comment documents — medium effort, occlusion-only benefit.
- **`descriptor_stride` ↑**, **`yolo_imgsz` ↓**, **`max_proc_long_edge` ↓**: all real
  speedups, all accuracy trade-offs. The shipped values are already reasonable for Orin.

## What NOT to do first

- Don't target DLA (Orin Nano has none).
- Don't chase pinned-memory / zero-copy transfer tricks — unified memory makes the
  copies cheap; fix the *syncs* instead.
- Don't downsize the SiamABC model or disable YOLO/OSNet/occlusion recovery as a first
  move — those are accuracy levers, not free wins.
- Don't benchmark with `run_single_video.py` / `--output_video` — the video writer and
  overlay panels ([vis/test_model.py:453+](../vis/test_model.py#L453)) dominate and hide
  real tracker cost. Use the `output_video=False` fast path.
- Don't ship a workstation-built TRT cache to the Orin — rebuild engines on-device
  (the cache prefix already fingerprints GPU identity + library versions, so it will
  correctly miss and rebuild — just make sure the cache dir is writable on-device).

## Jetson deployment "gold advice"

**Set the platform up before you measure anything:**

1. **Max the clocks.** `sudo nvpmodel -m 0` (MAXN) then `sudo jetson_clocks`. Without
   this you are benchmarking a throttled device and every number is wrong. Pin a fan
   curve; the Nano thermally throttles fast.
2. **Watch thermals/power while profiling** with `tegrastats` (or `jtop`). If GPU/CPU
   clocks droop mid-run, your latency variance is thermal, not code.
3. **On a 4 GB Nano, add zram/swap** and prefer the streaming submission writer (stdlib
   `csv`) over the pandas DataFrame build ([run_inference.py:1688](../run_inference.py#L1688))
   to avoid an OOM at the end of a long split.
4. **Build TRT engines once, on-device, to a writable local cache dir**, then reuse.
   First-run compile is minutes; warm runs load the `.ts` engines. Keep the cache off
   the Docker image.

**Methodology (so optimizations are real):**

5. **Measure on-device, warm, with caches built.** The numbers from the workstation
   don't transfer. Make `profile_components.py` use the *same* TRT cache args and
   *include frame decode time* as its own bucket — otherwise you'll "optimize" GPU work
   while a serialized `imdecode` dominates (this is exactly why finding #1 is invisible
   without decode timing).
6. **Lock a golden-output regression** (`tests/test_regression.py`) and diff per-frame
   bbox files after every change. "Behavior-preserving" is only true if the bytes match.
7. **Profile the split, not one clip.** The YOLO-reload and submission-memory issues only
   show up across many sequences.

**Suggested implementation order (all low risk first):**

- **Phase 0 — measure:** on-device warm profiling with decode timing + RSS + CUDA mem;
  save golden outputs.
- **Phase 1 — free wins:** decode prefetch thread (#1); `cudnn.benchmark` (#6); drop dead
  `albumentations` (#5); YOLO object cache (#2); kill `lam.item()` sync (#3); `box_coder`
  single `.item()` (#7).
- **Phase 2 — hot-path cleanup:** coalesce the 5–6 decode/postprocess syncs into one (#4);
  thread-count tuning (#10).
- **Phase 3 — deployment hardening:** `pyproject.jetson.toml` + L4T base image (#8);
  recursive `.dockerignore` incl. `*.ts` (#9); stream submission CSV (#12); fingerprint
  + optionally FP16 the YOLO engine (#11, benchmarked).

## Bottom line

The repo is already well-aimed at Jetson: the expensive vision models have FP16 TRT
paths, OSNet overlaps on a side stream, the descriptor work is strided and capped, and
the frame is pre-scaled. The remaining easy wins are **plumbing, not algorithms**:

- **overlap frame decode with compute** (biggest CPU-bound win, `[NEW]`),
- **stop reloading YOLO per clip** (biggest startup win, confirmed),
- **delete per-frame GPU syncs** — `lam.item()`, the `box_coder` doubles, and the
  postprocess copies (`[NEW]` + confirmed/sharpened),
- **turn on `cudnn.benchmark` and drop the dead `albumentations` import** (`[NEW]`, one-liners),

…then split the deps/container for JetPack. None of these change tracker behavior if
implemented carefully and checked against the golden regression. Save FP16-YOLO, INT8,
TF32, and any model-size change for a separate, *benchmarked* pass — they trade accuracy
for speed and are not "free."
